# Как проект принимает типовые требования

Проект выбирает профили каталога и для каждого требования один из трёх режимов. Выбор лежит в `adoption.yaml` в корне репозитория требований проекта, схема: [`schema/adoption.schema.json`](../schema/adoption.schema.json). Пример для выдуманного продукта x: [`adoption.yaml`](../adoption.yaml).

| Режим | Что делает проект | Что генерируется | Как трассируется |
|---|---|---|---|
| `inherit` | Принимает как есть и задаёт значения параметров | `requirements/_catalog/T-…md` с подставленными параметрами и `Needs: impl, itest` | Код и тесты проекта ставят `[impl->req~T-IAM-003~1]`, `[itest->req~T-IAM-003~1]` |
| `refine` | Пишет своё требование, которое уточняет типовое | Копия с `Needs: req`. Своё требование содержит `refines: [T-…]` и строку OpenFastTrace `Covers:` | Цепочка «типовое → требование проекта → код и тесты» |
| `waive` | Исключает | Ничего; строка в реестре с причиной | Не трассируется. CI проверяет причину, владельца и срок пересмотра |

Копии в `requirements/_catalog/` генерирует `scripts/generate.py`, руками их не правят. `generate.py --check` в CI падает, если копии устарели.

## Правила

- Каждое требование уровня MUST из выбранных профилей (с учётом `includes`) должно быть принято, уточнено или исключено. Иначе ошибка `adoption_coverage`.
- SHOULD и MAY проект принимает по выбору.
- Уровень можно понизить только в профиле класса, не в проекте. Проект вместо этого исключает требование.
- У исключения обязательны `reason`, `owner` (группа `role-…`) и `review` (дата пересмотра). После даты пересмотра CI падает (`waiver_expired`), пока исключение не продлят или не закроют. Поле `compensated_by` перечисляет требования проекта, которые частично закрывают риск. Исключение не служит образцом для других проектов, как исключения DNS в naming-standard.
- Приоритет по MoSCoW проект пишет в `priority` пункта (`M`, `S`, `C`, `W`).
- `catalog.release` фиксирует выпуск каталога. Обновление выпуска делается отдельным PR. Если ревизия требования выросла, OpenFastTrace покажет теги со старой ревизией в коде как устаревшие.

## Проверки blueprints

Типовое требование ссылается на строки матриц проверок blueprints в поле `checks`, например `ai-enablement#M6`. В копии для проекта эти ссылки остаются, поэтому в отчёте видно, какой строкой матрицы типовая архитектура проверяет требование, а в `links.verified_by` требования проекта — каким тестом или протоколом проект его закрыл.

## Новый проект из шаблона

1. Создайте репозиторий кнопкой «Use this template».
2. Удалите примеры продукта x из `requirements/` и замените префикс, типы и области в `reqs.config.yaml`.
3. Каталог (`catalog/`, `profiles/`, `sources.yaml`) пока должен лежать в том же репозитории: скрипты читают его оттуда. Обновляйте его из `mess-systems/requirements` по тегу выпуска и укажите выпуск в `catalog.release` файла `adoption.yaml`. Папку `assessments/` можно удалить.
4. `make register && make check`.

Чтение каталога из отдельного клона нужного выпуска пока не сделано, см. «Что дальше» в [catalog.md](catalog.md).
